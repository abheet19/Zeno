Policy & Approval Kernel

The deterministic engine that sits outside every model and is the only thing allowed to turn a proposal into an effect. Slice P1-01 — the first thing built, because everything else trusts it.

In plain words

Think of it as the security desk that sits between Zeno's “thinking” and the real world. The AI can think anything and propose anything — but it can never actually do something (push code, write a ticket, send a message) without walking up to this desk first. The desk checks how risky the action is, shows you exactly what will happen, waits for your yes, checks nothing changed while you decided, then lets it through once — and stamps a receipt. Payments and anything forbidden don't get a desk pass at all.

This slice builds only that desk — no screens, no AI, no internet. Small, boring, and provable, so the exciting parts on top can be trusted.

0Why this slice is first

Every promise in the suite — “Reason before action”, the approval capsule you clicked, the drift refusal, the receipt-gated seal — is this component. It is the policy engine that sits outside every model and is the only code permitted to cause an external effect.

If it is correct, no agent, model, bug, or prompt-injection can produce an unapproved or double-applied effect. If it is wrong, nothing above it can be trusted. So it is built first, alone, with no UI and no model, where it can be proven in isolation. It depends on nothing; everything else depends on it.

3The seven laws

Plain version: these are the seven promises the desk can never break — no matter what the AI says, what a web page tries to trick it into, or what bug exists upstream. They aren't guidelines; they're built into the structure, and each one is proven by an automated test.

Each is enforced structurally and each ships as a property test over randomized action streams.

  • L1No skip. No consequential action reaches COMMITTING without passing APPROVED for its own action hash.
  • L2One attempt. The executor runs exactly once. No retry loop, ever.
  • L3Compare-and-swap. At commit the base is re-read; if it drifted → REFUSED, approval unspent, nothing applied.
  • L4Single-use. An approval is consumed on use; a second use is denied.
  • L5Seal after receipt. VERIFIED is only reachable after a durable receipt is written — success can never render before its receipt exists.
  • L6No self-approval. The agent that proposes can never approve. This is the structural answer to prompt-injection: a malicious string reaches PREVIEWED at most, never COMMITTING.
  • L7T4 is absolute. Payments and prohibited actions reach only DENIED. No override path exists in code.

4Risk-tier policy

Policy is data, not code — one policy.json, schema-validated and hash-pinned: its hash lands in every receipt, so you can always prove which policy governed a decision. (Signing it comes with the later Signer slice — v1 doesn't pretend to have keys it doesn't.) Classification is deterministic and rounds up on ambiguity, never down.

5The receipt ledger

Plain version: a tamper-evident logbook. Every outcome — done, refused, denied — writes one line, and each line is cryptographically linked to the one before it (like a chain). If anyone edits or deletes a past line, the chain visibly breaks and Zeno can point to exactly where. This is also why a “success” checkmark can only appear after its logbook line exists — the tick is drawn from the receipt, never before it.

A single append-only JSONL file on the pilot's local disk — tamper-evident now, tamper-proof later (the Signer slice adds real signatures; v1 says exactly what it is). Every terminal outcome writes one hash-chained receipt; every approval is logged. Any edit or deletion breaks the chain, and verifyChain() localizes the first break.

{ id, actionHash, outcome:'verified'|'refused'|'denied'|'expired'|'outcome-unknown',
  reason, casBaseObserved, externalEffect, prevReceipt, selfHash, at }

Raw secrets never enter the ledger — a redact() pass records that a value existed, never the value. The selfHash is written by an injected Signer (plain SHA-256 now; a keypair/HSM in the later signing slice — the seam is left open).

6How you'll see it's done

  • Property tests for each of L1–L7 over randomized streams — e.g. no sequence ever reaches VERIFIED without a matching single-use approval.
  • CAS test: approve → mutate base → commit ⇒ REFUSED, approval unspent, zero effect.
  • Injection test: adversarial payloads never advance past PREVIEWED.
  • Chain test: corrupt one line ⇒ verifyChain() reports the exact break.
  • Determinism: same inputs + injected clock ⇒ byte-identical ledger (replayable).
  • The headless simulator drives every path the Gate-2 capsule shows — await→commit→verified and await→drift→refused — with no UI and no model.

7Simplicity pass — what v1 deliberately does NOT have

Plain version: reviewed for overcomplication. Everything cuttable was cut; every cut is a seam we can reopen later — none changes the seven laws.

  • No policy or receipt signing — hash-pinned and hash-chained instead; real keys arrive with the Signer slice.
  • No multi-approver, no delegation — one owner, one approval channel.
  • No database — one JSONL file. No plugin system. No config sprawl — just policy.json.
  • Binding verifies four fields (payload, base, target, tier); all provenance rides as one opaque hash — recorded and replayable, not individually validated.

The seven laws are the product. Everything else stays as small as honesty allows.
