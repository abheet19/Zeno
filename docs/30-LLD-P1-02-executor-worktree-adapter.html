Executor & Worktree Adapter

The kernel decides; this is the first hand that actually does the thing it approved — jailed to a sandbox, all-or-nothing, and it proves what it did rather than claiming it. Slice P1-02.

In plain words

P1-01 was the security desk that decides. This slice is the first hand that carries out an approved action — but a careful one: it only works inside a sandbox it can't escape, it does exactly one thing, all-or-nothing (never a half-finished write), and it proves the result by re-reading it.

If it can't prove the effect really happened, it says "outcome unknown" honestly instead of pretending. This is what turns "approve → verified" from a test stub into a real file changing on disk — and it's the exact pattern every future hand (git, Jira, browser) will copy.

0Why this slice is next

P1-01 can classify, preview, approve and commit — but in its tests the executor is a stub. The loop isn't closed: an approval has never driven a real effect. This gives the kernel its first real executor, so the whole chain runs end to end and you can see the result. It's deliberately the smallest possible real effect — a sandboxed file write — so the risky part (touching the world) arrives in the most contained, reversible, verifiable form before anything bigger.

2Reconcile — prove it, don't claim it

Plain version: the executor's word is not evidence — the re-read is. After it acts, it looks again to confirm the file truly matches what you approved. A lying or buggy executor gets caught here and can never report a false success.

apply(payload):
  1. jail-check   : resolve(root/relPath) must stay inside root   else path-escape
  2. base-check   : hash(current file) === expectBaseHash         else drift, refuse
  3. write-atomic : temp → fsync → rename over target             all-or-nothing
  4. reconcile    : hash(re-read) === expectPostHash ?
        yes → EffectProof{ effect: 'file:'+postHash }
        no  → throw  →  kernel records OUTCOME_UNKNOWN

Step 4 is what makes a dishonest executor harmless: if the file on disk doesn't actually match the approved post-state, the executor refuses to report success, and the kernel writes an outcome-unknown receipt with retry frozen — never a false verified.

3The three guarantees

  • JAILEDCannot escape the sandbox. Any target resolving (after symlinks) outside the configured root is rejected. ../../etc/passwd, absolute paths, escaping symlinks — all refused.
  • ATOMICAll-or-nothing. The real file is only ever replaced by an atomic rename of a fully-written temp. A crash mid-write leaves the original intact — never a half-file.
  • PROVENHonest. Success is reported only after the re-read matches. Idempotent: re-applying an already-applied effect is a safe no-op. On any error → outcome-unknown, never a silent retry.

4How you'll see it's done

  • Property tests (randomized): no generated path ever escapes the jail; a claimed-but-unreal result is always caught; re-apply never double-writes; an injected mid-write failure always leaves the original intact.
  • E2E (kernel + executor): approve → the file actually changes → verified receipt carries the real post-hash; base drifts → refused, file untouched; executor fed a tampering fs → outcome-unknown, retry frozen.
  • All checks green: strict typecheck, dependency-free lint (extended to forbid un-injected fs in the core), full tests, coverage, determinism.
